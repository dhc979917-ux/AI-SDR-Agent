# 真实 / 半真实通话评测

目标：用 20–30 条获得授权的通话，回答三个问题：

1. 企业抬头 Top-1、Top-3 和候选召回怎么样？
2. 高/中/低意向的混淆矩阵怎么样？拒联是否漏判？
3. 各字段的准确率、覆盖率和缺失情况怎么样？

## 1. 数据来源

优先级：

1. 题目提供的真实通话录音（如果作业允许使用）。
2. 你自己或团队获得授权的真实销售通话，去掉姓名、完整手机号、地址等敏感信息。
3. 半真实数据：用真实通话改写/加 ASR 常见错误（同音字、漏字、断句），但必须人工写 gold，不能拿模型输出当答案。

不要把真实客户数据提交到公开 GitHub。`eval/labeled_cases.json` 已被 `.gitignore` 排除；只提交 `eval/labeled_cases.example.json` 这种模板。

## 2. 标注格式

复制模板：

```bash
cp eval/labeled_cases.example.json eval/labeled_cases.json
```

每条记录：

```json
{
  "id": "R01",
  "split": "test",
  "transcript": "销售：...\n客户：...",
  "notes": "客户是品牌杭州经销商，经营主体待确认",
  "gold": {
    "company_accept": [
      "木里木外家具启东有限公司",
      "上海木里实业发展有限公司"
    ],
    "intent_level": "high",
    "do_not_contact": false,
    "fields": {
      "industry": "全屋定制",
      "area": "浙江省杭州市",
      "contact_name": "张总",
      "contact_title": null,
      "phone": "138xxxx1234",
      "mendian": null,
      "shejishi": null
    }
  }
}
```

规则：

- `company_accept` 是“可接受的企业抬头集合”，不是唯一答案。品牌方、经销商、分支机构都可能可接受；无法确定经营主体时，把可接受候选都列进去，并在 notes 说明。
- `intent_level` 只能是 `high`、`medium`、`low` 或 `null`。`null` 表示服务/无效/信息不足，不要强行标成低意向。
- `do_not_contact` 只有客户明确要求停止联系才为 true。
- 字段只标通话里明确确认的事实；没提到就写 `null`。不要根据品牌总部、电话归属地或常识推断。
- 电话号码保留脱敏形式；不要补造数字。
- `demand_summary` 不做逐字匹配，脚本暂不计分，人工抽查即可。
- `split` 建议固定为 `test`；不要一边看测试结果一边改 Prompt，否则就是过拟合。

## 2.1 从音频 ZIP 开始

音频 ZIP 只是输入，不是测试集；需要先转写、人工核对角色，再补 gold。

```bash
mkdir -p data/real_calls
unzip SDR真实通话录音.zip -d data/real_calls
ls data/real_calls
```

建议使用**独立的评测数据库**，不要混入真实业务库：

```bash
export SDR_DB_PATH="$PWD/var/eval.sqlite3"
export SDR_ASR_API_KEY=你的ASRkey
export SDR_LLM_API_KEY=你的文字模型key
.venv/bin/python -m sdr --host 127.0.0.1 --port 8878
```

打开 `http://127.0.0.1:8878`：

1. 进入「录音转写」，批量上传 `data/real_calls` 里的音频。
2. 等 ASR 完成，逐条核对销售/客户角色和文字；不要直接采用 AI 角色作为 gold。
3. 保存确认稿。
4. 导出确认稿为标注草稿：

```bash
.venv/bin/python scripts/export_transcripts.py   --db var/eval.sqlite3   --output eval/labeled_cases.draft.json
```

5. 把 `eval/labeled_cases.draft.json` 复制成 `eval/labeled_cases.json`，逐条人工补：
   - `company_accept`
   - `intent_level`
   - `do_not_contact`
   - `fields`

6. 跑评测：

```bash
.venv/bin/python scripts/evaluate_labeled.py   --dataset eval/labeled_cases.json   --mode rules   --entity-provider auto
```

注意：

- 如果你在分析前人工改了 ASR 文字，评测衡量的是“人工校对 + Agent”；如果直接用自动转写，才是端到端。两种结果可以分开报告。
- 不要把 `data/real_calls/` 或 `eval/labeled_cases.json` 提交到公开仓库；`.gitignore` 已排除。
- 音频 ZIP 如果包含真实客户信息，先脱敏再处理。

## 3. 20–30 条怎么选

建议覆盖这些切片，每条至少 2–3 条：

| 类型 | 示例 |
|---|---|
| 完整企业全称 | “我们公司全称是青禾空间设计（杭州）有限公司” |
| 品牌/简称 | “叫木里木外” |
| ASR 同音/错字 | “木里木外/木里木外家居/木里木外家具” |
| 多候选/地区冲突 | 客户说杭州，企查查候选在启东 |
| 经销商/分支机构 | 客户是品牌代理门店，不是品牌主体 |
| 查无此企业 | 客户说了一个不存在的品牌 |
| 高意向 | 痛点 + 下月试用 + 预算范围 + 加微信 |
| 中意向 | 有具体问题，但时间/预算不明确 |
| 低意向 | 随便问问、没有计划/预算 |
| 拒联 | 明确不要再联系 |
| 条件表达 | “预算没批，如果免费才试” |
| 竞品 | 已用竞品但想替换 |
| 售后/无效 | 账号无法登录、打错电话 |
| 销售话术 | 销售介绍产品，客户只回“嗯/好的” |

不要只挑模型表现好的案例；拒联、售后、缺失字段、冲突案例必须包含。

## 4. 标注流程

1. 先人工听录音或看转写，确认销售/客户角色；不要直接采用 AI 分角色结果作为 gold。
2. 先标企业可接受主体，再标意向等级和四维依据，最后标字段。
3. 企业抬头用企查查核对全称，但不要把“企查查第一名”直接当客户经营主体。
4. 对不确定的案例写 notes；不要为了凑标签强行判断。
5. 建议 20% 的案例由第二个人复核，分歧由第三人裁决；至少保留一条“双人一致”的记录。
6. 冻结测试集版本，记录日期和标注人；评测后不要修改同一份测试集再调 Prompt。

## 5. 运行评测

先配置模型和企查查：

```bash
export SDR_ENTITY_PROVIDER=auto
export QCC_MCP_TOKEN=...
export SDR_LLM_API_KEY=...
# 可选：SDR_ASR_API_KEY 仅影响录音入口，本评测用文本
```

规则模式（便宜、可复现，建议先跑）：

```bash
.venv/bin/python scripts/evaluate_labeled.py \
  --dataset eval/labeled_cases.json \
  --mode rules \
  --entity-provider auto
```

模型模式（真实抽取 + 重排）：

```bash
.venv/bin/python scripts/evaluate_labeled.py \
  --dataset eval/labeled_cases.json \
  --mode llm \
  --entity-provider auto
```

输出：

```text
eval/artifacts/labeled-eval.json
```

## 6. 指标口径

### 企业抬头

- **Top-1 accuracy**：预测的企业名称是否在 `company_accept` 中。
- **Top-3 recall**：前 3 个候选里是否有可接受主体。
- **Candidate recall**：全部候选里是否有可接受主体。
- **Auto-confirm precision**：自动确认的记录中，预测名称正确的比例。
- **False confirmation rate**：自动确认但预测错误的占比；这个指标比 Top-1 更重要。
- **Abstention rate**：进入 `ambiguous/unresolved/lookup_failed` 的比例。

### 意向

- 3×3（加 `null`）混淆矩阵。
- high/medium/low 的 precision、recall、F1 和 macro-F1。
- `do_not_contact_recall`：真实拒联中被正确识别的比例。

### 字段

对 `industry / area / contact_name / contact_title / phone / mendian / shejishi` 计算：

- precision：预测非空且正确的比例；
- recall：gold 非空且被正确预测的比例；
- coverage：预测非空占 gold 非空的比例。

`demand_summary` 不做逐字比较，人工抽查语义是否忠实。

## 7. 报告模板

在验收记录/README 里写：

```text
数据集：30 条授权通话，冻结于 2026-10-21，单人标注 + 20% 复核
企业抬头：Top-1 83.3%，Top-3 90.0%，候选召回 93.3%，自动确认精度 100%，误确认 0
意向：macro-F1 0.78，high recall 0.80，DNC recall 1.00
字段：industry coverage 90%，area 80%，phone 100%…
限制：30 条样本量小；只覆盖杭州/苏州全屋定制；未覆盖方言和强噪声
```

样本量小时要写置信区间或直接说明“仅作方向性参考”，不要宣称生产准确率。

## 8. 半真实数据怎么造

如果没有足够真实通话：

1. 选 10–15 条真实/授权转写；
2. 人工改写品牌、地区、预算、时间、竞品、拒联等变量；
3. 加入 ASR 常见错误（同音字、漏字、断句、语气词）；
4. 每条都人工写 gold，不能拿模型结果反推；
5. 明确标记 `split: semi_real`，不要和真实测试集混合报告。

半真实数据可以验证鲁棒性，但不能替代真实盲测。

## 9. 注意

- 不要把 `eval/labeled_cases.json` 上传公开仓库；它可能包含客户信息。
- 不要用同一批 20–30 条既调 Prompt 又当测试集；最好留 10 条完全不看。
- 不要只报告 Top-1；同时报告候选召回、覆盖率和误确认率。
- 自动确认只针对唯一完整全称 exact；品牌简称和多候选仍应走人工。
